# IMPLEMENT Mode

Implement the approved handoff directly with the provider's workspace write and command capabilities, then report objective facts.

- `IMPLEMENT` may run only when an active implementation handoff exists.
- Implement only the approved handoff and do not introduce new planning, architecture, tests, documentation, or cleanup outside its scope.
- Read the authoritative boolean `validation` from the active `workitem.md`; a missing legacy field means `true`.
- With `validation: true`, first inspect the approved task reference or prerequisite and its write scope in `.vscode/tasks.json`. Before invoking RunWorker, create or complete only explicitly authorized missing configuration and scripts, and confirm the selected process task matches the approved action, normalized target, owner, command, string-array args, and cwd; An explicit Clean-before-Build requirement requires both Clean and Build. Existing owners `AiFlow` and `buildRunEditor` are valid; use `AiFlow` for new tasks. Do not use a Worker call to discover an already observable missing prerequisite.
- If required configuration creation is not scoped, or an explicit source-only restriction prohibits a necessary configuration write, report the handoff inconsistency and need for a new PLAN through the existing failed-run lifecycle. Do not widen write scope, repair unrelated files, invent a substitute action, or execute validation directly.
- `.vscode/tasks.json` defines Worker tasks; `launch.json` is independent Start configuration and is neither required nor created for validation. With `validation: false`, missing configuration alone requires no task/configuration preparation or Worker call; preserve acceptance criteria and explicitly authorized non-automatic checks.
- Write files and execute approved workspace commands directly through the configured provider sandbox, subject to the approved validation strategy and repository rules.
- Perform approved changes and create or complete handoff-required validation artifacts and configuration before executing validation.
- With `validation: true`, execute only the automatic validation strategy and exact command or action defined in the approved handoff, after the approved changes and scoped prerequisites. Report the actual command or action and its result.
- If the handoff lacks a concrete automatic validation action, or that action cannot run or fails and the allowed correction does not resolve it, report the issue and end under the existing failed-run lifecycle; do not regularly finish as implemented. Do not invent a substitute action outside the handoff.
- A delivery/build command satisfies automatic validation only when PLAN explicitly designates that command and its result as the verification action in the handoff. Merely creating an artifact or reporting a delivery build does not satisfy `validation: true`. One explicitly designated execution may serve delivery and validation without a redundant second run.
- `validation: true` requires project-level Build, without prescribing a language, build system, tests, compiled output, or launch configuration; scoped prerequisites may be created during implementation.
- With `validation: false`, the absence of a Worker, build, test, project, or validation action cannot by itself fail the run. Acceptance criteria and explicitly authorized non-automatic checks remain applicable.
- Do not create or rewrite configuration merely because it is absent. Preserve existing valid configuration and foreign entries unless the handoff expressly scopes a change.
- Do not install dependencies or restore artifacts autonomously when user-controlled preparation is required by repository rules.
- With `validation: true`, automatic validation must use the registered RunWorker MCP tool and the approved `Worker Command:` and `Worker Target:`. Commands are Build; `.` denotes the root. Missing or ambiguous selection requires a new PLAN. Never infer or substitute the action or target.
- Invoke RunWorker with arguments named exactly `command` and `parameter`, then await its response. Never invoke the selected validation process directly through the provider shell. Worker Test is diagnostic, not a project-test runner.
- Build and required Clean pass only with WorkerResponse.Success true, embedded WorkerBuildResult.success true, explicit integer exitCode 0, and explicit string report ".ai-flow/BuildReport.txt"; output text does not determine success. Missing fields, malformed results, launch failures, and preflight failures fail verification.
- Build and Clean serialize exactly seven properties: `success`, nullable `exitCode` (explicit null when no process starts), `stdoutTail`, `stderrTail`, `stdoutTruncated`, `stderrTruncated`, and `report: ".ai-flow/BuildReport.txt"`. The tails are always non-null string arrays and the truncation flags are always booleans. Failed operations independently retain the last 30 logical lines and at most 2,000 .NET line-content characters per stream, excluding separators; retain the latest text, including a suffix of the earliest retained line when needed, without splitting a surrogate pair. Recognize CRLF/LF/CR, preserve whitespace, indentation, blank lines and order, and do not add omission markers or interpret diagnostics. A terminal separator creates no extra element. A flag is true only when failure output was discarded by either limit. Success always emits empty arrays and false flags; failures with no captured output do likewise. Previews may omit earlier errors; read the full report when more context is needed.
- Use the actual MCP response; prose, console output, cached files, and prior invocations cannot establish validation. The host requires matching invocation-local relay evidence before finalizing IMPLEMENT, including question continuations. Pending formal questions do not consume the handoff; a finalizing continuation requires evidence from that invocation. The last matching execution is decisive.
- Keep ordinary authorized implementation commands available. This rule does not technically disable every direct process in a write-capable provider sandbox.
- Run no automated tests when the handoff does not explicitly request them.
- Do not infer validation requirements from existing test projects or validation infrastructure.
- If a required Worker Build or validation fails because of the current changes and the correction remains in scope, make at most one targeted correction across the run and rerun only the failed operation once.
- If that operation still fails, end the run without additional correction or fallback validation loops.
- Every normally ended run consumes and archives the active implementation handoff, resets `planning_ready` to `false`, and leaves no active implementation handoff.
- A successful conclusion writes `status: implemented`; an unresolved Worker Build, validation, or dependency failure writes `status: failed`.
- `DEBUG` and `REPORT` remain available as follow-up actions under the existing lifecycle; another `IMPLEMENT` requires a new `PLAN`.
- Do not emit an Apply or completion handoff.
- Do not classify the result as Complete, Incomplete, Blocked, Implementation incomplete, or Further work is required.
- Report only implemented changes, transport results, performed Worker Build and validation results, checks that could not run, and known issues.

## Canonical Project Build Contract

- Load and apply `.ai-flow/tasks/BuildTask.md` before creating/changing Build or optional Clean configuration. Its project-operation, task-selection, result, and invocation-local evidence contract applies to this mode within its existing write authority.
- With `validation: true` (missing means true), ordinary automatic validation is mandatory complete-project Build, not a changed-file check. Standalone Validate cannot replace it. No composite Worker action or alias is supported.
- Clean is optional and must meaningfully remove only defined generated artifacts. Never generate an empty/no-op Clean on project discovery. Only explicit `Worker Clean Before Build: true` requests separate Clean then Build calls for the same normalized project target; absence/false means Build-only. Await Clean and never launch Build after its failure.
- STRUCTURE inspects available required configuration without making its absence a readiness gate. PLAN scopes missing/incomplete tasks and exact project commands, including both tasks and the reason when Clean is required. IMPLEMENT finishes actual source changes before preparing scoped configuration, then invokes Worker. DEBUG follows the authorized project Build strategy within its existing scope.
- Build-only requires the last matching successful Build in this invocation. Required Clean needs the latest matching successful Clean before the terminal successful Build. Later Clean or failed/malformed required steps invalidate older proof; allowed corrected retries may establish later proof. A finalizing question continuation requires the whole proof anew.
- With `validation: false`, missing configuration alone does not require preparation or Worker execution and cannot fail the run; preserve acceptance criteria and authorized non-automatic checks. Launch configuration is independent of Build validation; smoke tests are separate work.

## Canonical Launch Contract

Launch configuration is independent of Build validation and applies regardless of `validation`. Inspect only relevant application targets, executable evidence, expected exact `AiFlow Launch: <ProjectName>` name and presence in `.vscode/launch.json`. Do not infer an entry point from technology alone or generate launches for every solution member. Preserve unrelated/legacy entries and document properties. Missing launch configuration alone is not a general readiness blocker.

Load and apply `.ai-flow/tasks/LaunchTask.md` before creating or updating launch configuration, including AI proposals. Worker `Start` uses only an exact configured target name and explicit program, args, cwd and optional env. It reads configuration only, does not debug or implicitly Build/Clean, and rejects unsupported dependencies before process creation. Success means process creation only; no readiness check, exit wait, monitoring or automatic smoke test follows.

Inspect the approved launch write scope, load LaunchTask.md and create/update only those configurations after source changes. Preserve foreign entries and properties. Launch configuration does not authorize Start or smoke execution; use only the approved validation action.
