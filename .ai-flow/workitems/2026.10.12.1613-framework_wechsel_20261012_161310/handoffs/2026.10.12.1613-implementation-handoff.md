## Problem and resolved result

`qbook/qbook.csproj` currently targets .NET Framework 4.8 and produces `qbookStudio.exe`; `qbookCsScript/qbookCsScript.csproj` targets Framework 4.7.2. Existing book projects declare `net8.0` but still reference Framework assemblies from `Framework64` and the GAC, and the qBook Framework executable. Changing the declared target alone cannot establish a modern-runtime application.

Port the two projects in `qbookStudio.sln` to `net10.0-windows`, Windows x64, retaining WinForms and existing book behavior. Port their dependencies and the code paths used to generate, compile, load, execute, stop, and reload books. The user accepts necessary script changes and regenerated project files provided functions and data remain usable.

The following decisions are fixed:

1. Current supported Windows is the deployment platform; no Linux, Raspberry Pi, macOS, or ARM target is introduced.
2. Books remain inside the qBook process and continue using the existing qBook objects and UI. Cancellation is cooperative. Scripts and background operations must observe cancellation; arbitrary code that ignores cancellation is not guaranteed to stop.
3. Replace AForge camera capture with OpenCvSharp, which is already a dependency. Preserve the required `CameraControl` behavior: device selection, start/stop, live image, visibility transitions, frame notification, and snapshots.
4. SQLite is the required database. Preserve existing database files, schemas, logger behavior, and relevant query/custom-function behavior. Do not replace SQLite with another database or introduce EF Core as a redesign.
5. The five current book projects listed below remain functional. Historical backups and nested data copies are not alternative authoritative migration targets.
6. Preserve existing application behavior outside the required migration changes. Unused package references may be removed when their absence has been established in the currently compiled sources; that does not authorize deleting features or reviving excluded legacy code.

No new architecture decision is delegated to IMPLEMENT. Equivalent local implementation details and compatible package asset/version selection within these decisions remain ordinary implementation work. A requirement conflict must return through the workflow rather than expanding scope.

### 3. Replace thread termination with cooperative cancellation

1. Replace actual System.Threading.Thread.Abort calls in the listed active library code and GO83P05 sequencers with per-operation cancellation signals/tokens. Preserve public domain methods named Abort, Stop, Destroy, Connect and Resume where callers rely on them.
2. Make run/idle loops, reconnect waits, sequencer Wait helpers and blocking operations observe cancellation. Use cancellation-aware waits and close/dispose owned transports when necessary to release I/O. Replacing Abort with Interrupt alone is not sufficient for active loops.
3. Keep worker ownership until it has stopped; avoid starting a replacement worker while the previous one still accesses the same objects. Avoid self-join, waiting while holding a lock needed by the worker, or synchronous UI waits that require that UI thread to process callbacks.
4. Dispose token sources/resources after workers stop. Expected cancellation must not be logged as an application fault. Ensure finalization happens once rather than racing run completion against Abort/Destroy.
5. Preserve cleanup of controls, events, connections, camera frames and SQLite logger queues when stopping/rebuilding. Existing cancellation-aware sample sequencers should not be gratuitously rewritten.
6. Keep the agreed limitation explicit in behavior: user script loops must cooperate. Do not introduce a hidden native force-kill, detached stale thread, or process-isolation fallback.
