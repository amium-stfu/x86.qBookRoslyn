# Implementation Handoff: FOSS Hash Compatibility

## Goal

Make the deterministic FOSS manifest hash calculation work in the Windows PowerShell process started by the existing MSBuild release target on the GitHub-hosted runner.

## Confirmed Scope

- Update only `qbook/updateFossState.ps1`.
- Replace the use of the unavailable `Get-FileHash` cmdlet with direct .NET SHA-256 hashing for individual FOSS runtime files.
- Preserve the existing canonical manifest serialization, SHA-256 fingerprint format, approved baseline comparison, change reporting, and explicit approval workflow.
- Preserve compatibility with the existing `powershell.exe` invocation in `qbook/qbook.csproj`; do not change the build target to `pwsh`.

## Existing State To Preserve

- `qbookCode/qbookCode.csproj` already uses the portable `bin\` base output path and must not be changed in this implementation.
- The release workflow continues to supply `BuildRevision` and the release build continues to block when the current FOSS fingerprint differs from the approved baseline.
- The FOSS scope remains `qbook` and `qbookCsScript`; no dependency set or compliance baseline files are changed by this compatibility fix.

## Implementation Steps

1. Update `Get-FileHashValue` in `qbook/updateFossState.ps1`.
   - Open the supplied file for reading and calculate its SHA-256 digest with `[System.Security.Cryptography.SHA256]`.
   - Convert the digest to a lowercase, continuous hexadecimal string matching the format previously returned by `Get-FileHash`.
   - Dispose the file stream and SHA-256 instance reliably after the calculation.

2. Keep all callers of `Get-FileHashValue` unchanged.
   - Runtime-file manifest entries must retain their current `sha256` values for identical files.
   - Do not change component ordering, canonical JSON generation, fingerprint hashing, result-file format, baseline parsing, or approval behavior.

## Acceptance Criteria

- The FOSS validation target no longer depends on the `Get-FileHash` cmdlet.
- `updateFossState.ps1` can calculate file hashes when started through the existing Windows PowerShell MSBuild command on the hosted runner.
- For unchanged restored dependencies and distributed files, the generated manifest fingerprint remains equal to the checked-in approved baseline fingerprint.
- A changed FOSS-relevant file or dependency still causes the existing baseline mismatch and prevents the official release build.

## Verification

No automated validation is registered for this solution. As resolved in STRUCTURE, the user manually dispatches the GitHub Actions release workflow and evaluates its workflow result and uploaded artifact.
