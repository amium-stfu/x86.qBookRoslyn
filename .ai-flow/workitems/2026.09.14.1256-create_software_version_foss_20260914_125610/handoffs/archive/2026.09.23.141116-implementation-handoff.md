# Implementation Handoff: Consolidated Local Release Tooling

## Goal

Consolidate the local qbook release tooling in `build/release` while keeping the source-controlled release state in the solution-root `NugetRevision.json`. Extend the local release entry point so the user can optionally replace the Major and Feature revisions through English interactive prompts before the release state is updated and the release is built.

The release version remains `Major.Feature.Foss.yyDDD`. `yyDDD` is the two-digit year followed by the zero-padded day of year. `FossRevision` remains automatically incremented when the deterministic effective FOSS state changes. `BuildId` remains automatically incremented for every local release and is written to `BuildInfo.md` only.

## Scope and constraints

- The official release covers qbook and qbookCsScript. Visual Studio Debug builds remain unchanged.
- Release execution remains local. The removed GitHub release workflow must not be restored.
- Keep `NugetRevision.json` in the solution root. The script changes this checked-in state; the user reviews and commits it after a release.
- A changed FOSS state does not block a local release, does not perform a legal approval, and does not generate an HTML FOSS report.
- Keep the existing deterministic SHA-256 FOSS-state calculation and its current component discovery scope.
- Do not move or alter `generateNuGetPackageReport.ps1`; it remains part of the existing qbook project build behavior rather than the consolidated release workflow.
- Do not introduce a new project, a CI workflow, or an ESP-specific implementation.

## Affected files

Move the following existing release workflow scripts from `qbook` to `build/release`:

- `release.ps1`
- `updateFossState.ps1`
- `updateAssemblyInfo.cs.ps1`
- `updateBuildInfo.ps1`
- `packageRelease.ps1`

Update these consumers and state files:

- `NewRelease.bat`
- `qbook/qbook.csproj`
- `qbookCsScript/qbookCsScript.csproj`
- `NugetRevision.json`

## Implementation sequence

1. Create `build/release` and relocate the five release workflow scripts listed above. Preserve their responsibilities and command ordering: update state, build qbook Release, create `BuildInfo.md` in `Setup/Release/bin/qbook`, then package the release archive.

2. Make every relocated script resolve the solution root and the qbook-specific input/output locations correctly from its new directory. In particular:

   - The release entry script must locate `qbookStudio.sln`, `NugetRevision.json`, `Setup`, and `qbook` from the solution root.
   - The FOSS-state script must continue to discover package declarations in both qbook projects, runtime package trees, and the qbook-owned `PdfSharp.dll` and `ThirdPartyNotices.txt` files.
   - The assembly-version script must still generate the per-project generated assembly-info file passed by MSBuild.
   - Build-info and packaging must continue to use the release output directory and root state file passed by the release entry script.

3. Update `qbook/qbook.csproj`:

   - Replace the five old `None` script entries with their `build/release` locations.
   - Update `GenerateAssemblyVersionInfo` to execute `build/release/updateAssemblyInfo.cs.ps1`.
   - Pass qbook's `obj/GeneratedAssemblyVersionInfo.cs` explicitly as the output path so relocating the script cannot change the generated-file location.
   - Retain the existing root `NugetRevision.json` argument.

4. Update `qbookCsScript/qbookCsScript.csproj` so its Release-only `GenerateAssemblyVersionInfo` target executes the relocated assembly-version script. Keep its existing explicit qbookCsScript generated-file output path and root revision-state argument.

5. Update `NewRelease.bat` so it invokes `build/release/release.ps1` as the local user entry point.

6. Add the interactive Major and Feature revision handling to `build/release/release.ps1`, before the FOSS-state update:

   - Read the current state from root `NugetRevision.json`.
   - Prompt exactly in English with `Change major revision? (y/n)` and then, independently, `Change feature revision? (y/n)`.
   - For each affirmative `y`, prompt for the replacement numeric revision value. For `n`, retain the current value.
   - Reject invalid answers and invalid replacement values with English errors. Revision values must be non-negative integers not greater than `65535`, matching the technical assembly-version limits already enforced by the state and assembly-version scripts.
   - Pass the selected Major and Feature values to the FOSS-state update so that the state update, automatic Foss revision decision, BuildId increment, fingerprint, and manifest are persisted together in `NugetRevision.json`.
   - Preserve the current failure behavior: a missing or malformed state, invalid input, missing required FOSS component, or failed build/package stops the release with an English error.

7. Adjust `build/release/updateFossState.ps1` only as needed to accept the selected Major and Feature values from the release entry script. It remains the single writer of `NugetRevision.json`, retains the existing validation and SHA-256 fingerprint calculation, increments `fossRevision` only when the fingerprint changes, and increments `buildId` for every local release.

8. Ensure `BuildInfo.md` remains generated only in the final qbook release output directory and retains the release version, UTC timestamp, source commit, FOSS revision, FOSS fingerprint, and Build ID. The package archive continues to include the output and accompanying release metadata as it does today.

9. Remove the obsolete script copies from `qbook` after all project, batch, and intra-script references point to `build/release`. Do not remove unrelated qbook PowerShell tooling.

## Acceptance criteria

- The only local release command exposed by `NewRelease.bat` starts `build/release/release.ps1`.
- The five release workflow scripts are located in `build/release`; `NugetRevision.json` remains in the solution root.
- A local release asks both English Major and Feature change questions. Answering `n` preserves the stored value; answering `y` requires a valid replacement value.
- Major, Feature, and Foss revisions remain valid .NET four-part assembly-version components (`0` through `65535`).
- A Release build of both qbook projects receives the same generated `Major.Feature.Foss.yyDDD` version from the root state, while Debug behavior remains unchanged.
- An unchanged deterministic FOSS manifest preserves `fossRevision`; a changed manifest increments it and still continues the local release.
- Every local release increments `buildId`, and the final qbook release directory contains `BuildInfo.md` with the specified traceability fields.
- The local release workflow does not perform FOSS approval, generate an HTML FOSS report, automatically commit changes, or recreate the GitHub release workflow.

## Validation

No registered automated validation is available for this workitem. The user performs the local release verification after implementation, including the interactive prompt paths and the produced release output.
