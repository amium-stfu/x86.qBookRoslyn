# Implementation Handoff: GitHub Actions FOSS Release

## Goal

Make GitHub Actions the sole producer of official qbook Release artifacts. Debug builds remain unchanged and run locally through Visual Studio. A manually started GitHub Actions Release workflow restores packages on a Windows runner, validates the approved FOSS state, supplies its run number as `BuildRevision`, and creates the qbook Release artifact.

## Scope

### Included

- The official qbook Release, including `qbookCsScript`.
- The existing FOSS fingerprint scripts and source-controlled `compliance/foss` baseline/manifests.
- A manually dispatched GitHub Actions workflow on a Windows runner.
- A PowerShell Release entry script called by that workflow.
- Explicit FOSS approval by a reviewer through a pull request and merge.

### Excluded

- Local Visual Studio Debug version changes or Debug build behavior.
- `qbook-publisher`, `VScodePlugin`, npm dependencies, legal review, automatic FOSS approval, dependency changes, package migration, and broad compliance/SBOM infrastructure.
- Automated tests and automated functional validation; the user performs functional verification of the release workflow.

## Affected files

| Path | Required change |
|---|---|
| `.github/workflows/release-qbook.yml` | New manual GitHub Actions workflow for official qbook Releases. |
| `qbook/release.ps1` | New PowerShell Release entry script invoked by the workflow. |
| `qbook/updateFossState.ps1` | Retain and complete the deterministic FOSS state validation used by Release builds. |
| `qbook/approveFossState.ps1` | Retain and complete the explicit baseline-generation command used by the reviewer before opening a pull request. |
| `qbook/updateAssemblyInfo.cs.ps1` | Retain Release version generation from validated FOSS state and supplied `BuildRevision`; retain Debug behavior. |
| `qbook/qbook.csproj` | Retain the Release-only FOSS preflight and generated AssemblyInfo integration. |
| `compliance/foss/approved-state.json` | Created and versioned only by the explicit reviewer approval flow. |
| `compliance/foss/manifests/<fingerprint>.json` | Created and versioned only by the explicit reviewer approval flow. |

## Implementation sequence

1. Complete the existing FOSS-state implementation in `qbook/updateFossState.ps1` and `qbook/approveFossState.ps1` without replacing the PowerShell approach.
   - The Release check covers `qbook` and `qbookCsScript` package declarations, package-provided runtime files, Roslyn `BuildHost-netcore`, `qbook/PdfSharp.dll`, and `qbook/ThirdPartyNotices.txt`.
   - The canonical manifest remains deterministic: stable component ordering and property ordering, UTF-8 without BOM, LF line endings, no machine paths or timestamps, and SHA-256 fingerprinting.
   - Release validation reads the committed baseline and fails with the deterministic added/removed/changed component diff when the fingerprint differs.
   - The approval script is explicitly reviewer-operated. It creates the immutable manifest and current baseline, increments `FossRevision`, and never runs from the Release workflow or MSBuild.
   - The first Release must remain blocked until a reviewer has created and merged the initial approved baseline.

2. Preserve the existing qbook Release build integration.
   - `qbook/qbook.csproj` must run FOSS validation only for `Release` before generated AssemblyInfo compilation and fail if the baseline is absent, malformed, or mismatching.
   - `qbook/updateAssemblyInfo.cs.ps1` must keep Debug behavior unchanged. For Release it consumes the validated FOSS-state result and a supplied numeric `BuildRevision`.
   - Produce the informational product version as `yy.FossRevision.BuildRevision`, for example `26.09.00125`, and the numeric .NET assembly/file version as `26.9.125.0`.
   - Reject invalid revision components, including values outside .NET assembly-version limits. The scripts must not derive a revision from local time or persist a BuildRevision counter.

3. Add `qbook/release.ps1` as the official Release entry point.
   - Accept `BuildRevision` as a mandatory input and validate it before invoking the Release build.
   - Invoke the existing qbook Release build using the Visual Studio/MSBuild toolchain available on the Windows runner, passing `BuildRevision` as the MSBuild property.
   - Rely on the existing Release targets to invoke the FOSS check and generated AssemblyInfo script. Do not duplicate FOSS discovery, approval, or version-generation logic in this entry script.
   - Fail on any build or FOSS validation error and leave approval files unchanged.

4. Add `.github/workflows/release-qbook.yml` based on the existing GitHub workflow style.
   - Use `workflow_dispatch` only; pushes must not create official releases automatically.
   - Use `windows-latest`, check out the manually selected ref, and make the workflow run number available to `qbook/release.ps1` as `BuildRevision`.
   - Restore the legacy NuGet packages before FOSS validation because hosted runners begin without the ignored `packages` directory. This restore belongs to the GitHub Release workflow; it does not change the local no-restore workspace verification rule.
   - Invoke `qbook/release.ps1` after restore.
   - Upload the generated Release output as the workflow artifact only when the script succeeds. A FOSS mismatch or build failure must not upload an official Release artifact.
   - Keep workflow permissions read-only; the workflow must not create, approve, commit, merge, or modify the FOSS baseline.

5. Document the reviewer-operated baseline handoff in the scripts' existing command output where necessary.
   - After external FOSS review, the reviewer runs `approveFossState.ps1` on the reviewed dependency state, commits only the generated `compliance/foss` baseline and manifest files on a branch, and opens a pull request.
   - A merged pull request is the sole approval event. A subsequent manually dispatched Release workflow validates the new committed baseline before building.

## Acceptance criteria

- Local Debug builds remain independent of `BuildRevision`, GitHub Actions, and FOSS baseline availability.
- A manual GitHub Release workflow restores packages, uses its own run number as `BuildRevision`, and invokes the PowerShell Release entry script on a Windows runner.
- A matching approved FOSS state produces an official artifact whose version includes the approved FOSS revision and workflow build revision.
- A missing baseline, malformed baseline, unresolved required dependency, changed FOSS fingerprint, invalid revision, or failed build blocks the official artifact upload.
- A changed FOSS state reports a deterministic technical diff and can become approved only through the reviewer-created and merged baseline pull request.
- The Release workflow has no permission or code path that automatically approves or changes FOSS state.
- No automated tests are added or run by this work; functional workflow verification remains user-owned.

## Constraints

- Preserve the existing PowerShell-based FOSS implementation and qbook MSBuild integration; do not introduce a separate compliance platform or a local revision counter.
- Do not modify the protected shared Amium item files listed in `AGENTS.md`.
- Do not change qbook-publisher, the VS Code plugin, or dependency versions.
