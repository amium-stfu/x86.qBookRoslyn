# Implementation Handoff: Create Software Version FOSS

## Goal

Make the manually dispatched GitHub Actions release workflow build successfully on its hosted Windows runner while preserving the established FOSS-versioning and approval workflow. The release build must not depend on the developer-specific `B:` checkout path.

## Confirmed Scope

- The official release remains limited to `qbook` and `qbookCsScript`.
- Retain the existing FOSS state workflow: deterministic dependency fingerprint, checked-in approved baseline and manifest, explicit reviewer pull-request approval, and a blocked official release when the fingerprint changes.
- Retain the version format `yy.FossRevision.BuildRevision`; the workflow supplies the monotonically increasing build revision from its run number.
- Retain the manual GitHub Actions release workflow, its restore step, and its Windows-hosted Visual Studio/MSBuild build.
- Correct the `qbookCode` SDK project's release output configuration so it is portable between a local checkout and the GitHub runner. `qbookCode` is built as a dependency of the release solution, although it is not an additional official release artifact.

## Non-Goals

- Do not change the FOSS dependency set, fingerprint schema, approval baseline, or approval procedure.
- Do not automatically approve a changed FOSS state.
- Do not change normal Visual Studio Debug-build behavior beyond removing the machine-specific output-path dependency.
- Do not update GitHub Actions versions solely because of the Node.js deprecation warning.
- Do not add tests, a new SBOM platform, GitHub Release publishing, or broader build/deployment changes.

## Affected Files

| File | Change |
| --- | --- |
| `qbookCode/qbookCode.csproj` | Replace the absolute `BaseOutputPath` that points to `B:\x86.qBookRoslyn\qbookCode\bin\Release` with the project-local standard base output path `bin\`. |

## Implementation Steps

1. Update `qbookCode/qbookCode.csproj`.
   - Change only the `BaseOutputPath` property in the existing primary property group.
   - Use `bin\` as the base output path so MSBuild derives the active configuration and target-framework directories within the checkout.
   - Do not alter the existing post-build copy to `Setup\Release\bin\qbookCode`; it must continue consuming `$(TargetDir)`.

2. Leave the existing release infrastructure unchanged.
   - Keep `qbook/release.ps1` using `vswhere` discovery including prerelease instances and selecting the discovered `MSBuild.exe`.
   - Keep `.github/workflows/release-qbook.yml` as the manually dispatched workflow that restores packages, passes `github.run_number` to `release.ps1`, and uploads the `Setup\Release\bin\qbook` artifact only after success.
   - Keep the existing FOSS scripts, compliance baseline files, assembly-version target, and approved-state validation unchanged.

## Acceptance Criteria

- The release solution no longer attempts to create or copy files to `B:\x86.qBookRoslyn` on a hosted runner.
- `qbookCode` produces its build output below its repository checkout and its existing post-build step can populate its release staging directory from `$(TargetDir)`.
- A manually dispatched GitHub Actions release run can proceed beyond the former `MSB3191`, `MSB3021`, and `MSB3027` errors caused by the unavailable `B:` path.
- The workflow still uses its assigned run number as `BuildRevision`, and release builds still require a matching approved FOSS fingerprint before version generation.

## Verification

No automated validation is registered for this solution. As resolved in STRUCTURE, the user manually dispatches the GitHub Actions release workflow and evaluates the resulting workflow status and uploaded artifact.
