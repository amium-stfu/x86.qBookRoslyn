# Implementation Handoff: Create Software Version FOSS

## Goal

Implement an automatic FOSS-state gate for the official qbook Release build. It must calculate a deterministic fingerprint for qbook and its referenced qbookCsScript dependencies, permit Release only when that fingerprint matches an explicitly approved baseline, and generate the approved product version `yy.FossRevision.BuildRevision`.

FOSS approval is an explicit separate operation. A Release build must never approve or update a changed FOSS state.

## Scope

### Included

- FOSS-relevant package state from `qbook/packages.config` and `qbookCsScript/packages.config`.
- Package-supplied runtime files distributed with qbook, including CEF/Chromium, OpenCvSharp, SQLite, and Roslyn `BuildHost-netcore`.
- Separately distributed `qbook/PdfSharp.dll` when it is part of the release output.
- `qbook/ThirdPartyNotices.txt`.

### Excluded

- `qbook-publisher`, `VScodePlugin`, npm dependencies, legal review, automated approval, package migration, SBOM platform work, dependency changes, and unrelated deployment changes.

## Files

| Path | Required change |
|---|---|
| `qbook/updateFossState.ps1` | New canonical state discovery, manifest generation, fingerprint comparison, diff reporting, and transient validated build-state output. |
| `qbook/approveFossState.ps1` | New explicit-only approval command. |
| `compliance/foss/approved-state.json` | New source-controlled current approved baseline. |
| `compliance/foss/manifests/<fingerprint>.json` | New source-controlled immutable manifests. |
| `qbook/updateAssemblyInfo.cs.ps1` | Replace Release timestamp version generation with validated FOSS state and pipeline build revision inputs. |
| `qbook/qbook.csproj` | Run the FOSS preflight for Release before generated AssemblyInfo creation. |

Do not modify `qbookCsScript/qbookCsScript.csproj`; it is an input to the qbook preflight. Do not modify the protected shared Amium item files listed in `AGENTS.md`.

## Implementation steps

1. Add `qbook/updateFossState.ps1` following the existing qbook PowerShell-script style.
   - Read only the two scoped `packages.config` files as package declarations.
   - Resolve restored packages below the repository `packages` directory. Enumerate the package files that are copied into the qbook Release output and the explicitly scoped non-package files.
   - Emit components with stable logical release path, component type, package ID/version where applicable, and SHA-256 content hash. Never include absolute paths, timestamps, machine data, or unordered data in the canonical content.
   - Sort by stable component identity. Serialize a fixed-schema JSON manifest with stable property order, UTF-8 without BOM, and LF line endings; calculate its SHA-256 fingerprint.
   - Read `compliance/foss/approved-state.json` and compare the fingerprint. A missing, malformed, incomplete, or mismatching state must fail with a clear English error.
   - On mismatch, print a deterministic component-identity diff for added, removed, and changed component metadata or file hash, then exit non-zero.
   - On match, write a transient validated result below `qbook/obj` containing `FossRevision`, the matched fingerprint, and the repository-relative approved manifest path. This file is build output only and must not be source controlled.

2. Add the versioned compliance state.
   - Create `compliance/foss/approved-state.json` as the sole current approval pointer with `fossRevision`, fingerprint, approval commit, approval timestamp, and repository-relative manifest path.
   - Store each approved canonical manifest under `compliance/foss/manifests` using its fingerprint as filename.
   - Normal builds must only read these files.

3. Add `qbook/approveFossState.ps1` as the only approval path.
   - Reuse the state-discovery and canonical-manifest path from `updateFossState.ps1` through an explicit script mode; do not duplicate discovery or hashing logic.
   - Require a complete current state and reject a fingerprint already equal to the approved baseline.
   - Increment the approved numeric `FossRevision`, persist the immutable manifest, then update the baseline to the new fingerprint and record the current Git commit and approval timestamp.
   - Do not invoke this script from MSBuild. User-visible confirmation and failure messages must be English.

4. Update `qbook/updateAssemblyInfo.cs.ps1`.
   - Preserve existing Debug behavior.
   - For Release, require the validated transient FOSS build-state result and a pipeline-provided numeric `BuildRevision`; do not use timestamps or maintain a local counter.
   - Read `FossRevision` only from the validated result. Validate both revision components against .NET assembly-version limits.
   - Generate the zero-padded product/informational version, such as `26.09.00125`. Generate numeric assembly/file version `26.9.125.0`; retain the Git commit suffix in `AssemblyInformationalVersion`.
   - Do not calculate, increment, or persist any revision in this script.

5. Integrate preflight and version generation in `qbook/qbook.csproj`.
   - For Release only, invoke `updateFossState.ps1` before `GenerateAssemblyVersionInfo`, directing it to the transient `obj` result. Its non-zero exit must stop the build before compilation.
   - Require `BuildRevision` as an MSBuild property supplied by the Release pipeline.
   - Pass the transient FOSS build-state result and `BuildRevision` to `updateAssemblyInfo.cs.ps1`.
   - Keep Debug flow, existing restore behavior, output-copy targets, and the qbookCsScript project reference unchanged except for this required Release integration.

## Acceptance criteria

- Identical restored dependency and distributed-file states produce byte-identical canonical manifests and the same SHA-256 fingerprint regardless of machine path, time, or enumeration order.
- A matching baseline permits Release and uses its approved FOSS revision with the pipeline `BuildRevision`.
- A package or included third-party-file change, addition, or removal emits a deterministic diff and prevents Release.
- Normal Release builds never modify the baseline or approved manifests.
- Only the explicit approval operation can create a new baseline and increment `FossRevision`.
- Multiple builds can produce `26.09.00123`, `26.09.00124`, and `26.09.00125` for one FOSS revision; a newly approved state then uses the incremented revision, for example `26.10.00126`.
- Missing baseline, unresolved package or required distributed file, malformed state, invalid revision, or absent `BuildRevision` fails Release clearly without approving a state.

## Validation

No validation is registered in the workitem validation registry. Do not add unregistered test commands to this handoff.
