# Implementation Handoff: Create Software Version FOSS

## Goal

Add a release-build FOSS-state gate for the official qbook release. The gate must calculate a deterministic fingerprint for the FOSS-relevant state of `qbook` and its referenced `qbookCsScript` project, permit a Release build only when that fingerprint matches an explicitly approved baseline, and generate the approved `yy.FossRevision.BuildRevision` product version.

FOSS approval remains a separate explicit operation. A regular Release build must never create or update an approval baseline.

## Scope

### Included release components

- `qbook`, including all FOSS-relevant NuGet packages resolved from `qbook/packages.config`.
- `qbookCsScript`, including all FOSS-relevant NuGet packages resolved from `qbookCsScript/packages.config`.
- Third-party files that are distributed with qbook outside the normal package declarations:
  - package-provided native and managed runtime files copied to the qbook output, including CEF/Chromium, OpenCvSharp, SQLite, and Roslyn `BuildHost-netcore`;
  - `qbook/PdfSharp.dll` when it is included in the release output;
  - `qbook/ThirdPartyNotices.txt`.

### Explicitly excluded

- `qbook-publisher` and its separate solution.
- `VScodePlugin` and its npm dependencies.
- Legal review, license classification, and automated approval.
- Dependency changes, migration from `packages.config`, SBOM platform work, or unrelated release/deployment changes.

## Affected files

| Path | Change |
|---|---|
| `qbook/updateFossState.ps1` | New PowerShell implementation that discovers the scoped dependency state, emits the canonical manifest, hashes it, compares it to the approved baseline, writes the validated build-state result under `obj`, and returns a Release-blocking failure on a mismatch. |
| `qbook/approveFossState.ps1` | New explicit-only PowerShell command that accepts the currently generated state after external review, increments `FossRevision`, writes its immutable manifest, and updates the approved baseline. It must not be invoked from MSBuild or a normal Release build. |
| `compliance/foss/approved-state.json` | New source-controlled approved baseline containing the current `fossRevision`, fingerprint, approval commit, approval timestamp, and immutable manifest reference. |
| `compliance/foss/manifests/<fingerprint>.json` | New source-controlled immutable canonical manifest for each approved FOSS state. |
| `qbook/updateAssemblyInfo.cs.ps1` | Replace timestamp-based Release version creation with parameters for the approved `FossRevision` and pipeline-supplied `BuildRevision`; preserve Debug behavior. |
| `qbook/qbook.csproj` | Invoke the FOSS preflight before the existing generated AssemblyInfo target for `Release`; pass its approved revision to the version script and retain the existing generated source inclusion. |

No change is required to `qbookCsScript/qbookCsScript.csproj`: its package configuration is input to the qbook Release preflight.

## Required implementation sequence

1. Create `qbook/updateFossState.ps1` using the existing PowerShell-script style in `qbook`.
   - Read only `qbook/packages.config` and `qbookCsScript/packages.config` as package declarations for this release scope.
   - Resolve each package from the repository `packages` directory after package restore. Do not use absolute local paths in manifest content.
   - Enumerate only the package files and explicitly identified third-party files that are copied into the qbook Release output. Include the copied Roslyn `BuildHost-netcore` files defined by `qbook.csproj`.
   - For every manifest component, record a stable logical release path, component type, source package ID/version where applicable, and SHA-256 file digest.
   - Fail with a clear English error if a declared package or required distributed file cannot be resolved or hashed. Do not produce a successful fingerprint from an incomplete state.
   - Sort components by stable component identity and serialize a fixed-schema JSON document using stable property ordering, UTF-8 without BOM, and LF line endings. Exclude timestamps, absolute paths, machine-specific data, and unordered collections from the hashed content.
   - Calculate the SHA-256 fingerprint from that canonical manifest. Compare it exactly with `compliance/foss/approved-state.json`.
   - On a mismatch, produce a deterministic diff keyed by component identity (added, removed, or changed metadata/file hash), then terminate with a non-zero exit code.
   - On a match, write a generated `obj` build-state result containing the approved `FossRevision`, current fingerprint, and canonical manifest path. It is transient build output, not source-controlled state.

2. Add the source-controlled FOSS-state storage under `compliance/foss`.
   - `approved-state.json` is the single current approval pointer; it contains the approved revision, fingerprint, approval commit, approval timestamp, and a repository-relative manifest path.
   - Store every approved canonical manifest under `compliance/foss/manifests` using its fingerprint as filename.
   - Keep the baseline and manifests reviewable in source control. A normal build must read them only.

3. Create `qbook/approveFossState.ps1` as the explicit approval operation.
   - Reuse the same canonical-state generation as the Release preflight through an explicit script mode; do not implement a second discovery or hashing algorithm.
   - Require an existing, complete current manifest and a successful fingerprint calculation.
   - Reject approval when the current fingerprint is already the approved fingerprint.
   - Increment the currently approved numeric `FossRevision`, persist the canonical manifest at the fingerprint path, and atomically update `approved-state.json` to reference it.
   - Record the current Git commit and approval timestamp in the baseline for traceability.
   - Make its user-visible confirmation and failure messages English. It is the only implementation path allowed to change approved FOSS state.

4. Update `qbook/updateAssemblyInfo.cs.ps1`.
   - Keep the existing Debug `BaseFileVersion` path unchanged.
   - For `Release`, require the validated generated FOSS build-state result and `BuildRevision` inputs instead of obtaining a timestamp. Read `FossRevision` only from that result and validate it together with `BuildRevision` as numeric .NET assembly-version components.
   - Construct the display/informational version as zero-padded `yy.FossRevision.BuildRevision`, for example `26.09.00125`.
   - Generate numeric assembly/file version `yy.FossRevision.BuildRevision.0`, which is represented by .NET as `26.9.125.0`; use `AssemblyInformationalVersion` for the zero-padded product version and the existing Git commit suffix.
   - The script must not calculate, increment, or persist either revision.

5. Integrate the gate in `qbook/qbook.csproj`.
   - For `Release` only, execute `updateFossState.ps1` before `GenerateAssemblyVersionInfo`, direct it to write the generated FOSS build-state result under `obj`, and make a failed state check fail the build before compilation proceeds.
   - Accept `BuildRevision` as a required MSBuild property supplied by the Release pipeline. Do not create a local counter file and do not derive the revision from the build time.
   - Pass the generated FOSS build-state result and the pipeline `BuildRevision` into `updateAssemblyInfo.cs.ps1`.
   - Do not alter the existing Debug build flow, package restore behavior, output-copy targets, or project reference to `qbookCsScript` beyond what is needed to invoke the FOSS preflight.

## Acceptance criteria

- The same restored release dependency state always produces byte-identical canonical manifest content and the same SHA-256 fingerprint, independent of machine path, build time, or input enumeration order.
- A Release build with a fingerprint matching the committed baseline is allowed and emits the approved FOSS revision together with the pipeline-supplied build revision.
- A changed package, a changed included third-party file, or an added/removed included third-party release file produces a deterministic component diff and prevents an official Release build.
- No regular Release build changes `approved-state.json` or an approved manifest.
- The explicit approval command is required to establish a new baseline and increments only `FossRevision`.
- Consecutive approved-state Release builds can produce `26.09.00123`, `26.09.00124`, and `26.09.00125` from distinct pipeline revisions while retaining FOSS revision `09`.
- After explicit approval of changed state, subsequent releases use the incremented FOSS revision, for example `26.10.00126`.
- Missing baseline, missing package content, missing required distributed file, malformed baseline, invalid revision, or absent `BuildRevision` fails the Release path clearly and does not permit an unofficially approved version.

## Constraints

- Use PowerShell and the current qbook MSBuild integration pattern; do not add a general-purpose compliance framework.
- Consider package declarations as discovery input, but fingerprint the effective files distributed by the release rather than only project-file text where those files are available.
- Keep FOSS-state persistence in source control for auditability and historical traceability.
- Do not modify the protected shared Amium item files named in `AGENTS.md`.
- No registered automated validations exist for this solution. Do not add, propose, or execute unregistered validation commands as part of this handoff.
