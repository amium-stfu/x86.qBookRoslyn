# Implementation Handoff: Local Release Versioning and FOSS Snapshot

## Goal

Replace the hosted GitHub release path with a manually started local release script. The script must update a source-controlled dependency snapshot and produce the same valid four-part version for the official `qbook` and `qbookCsScript` release assemblies:

`MainRevision.FossRevision.yy.DayOfYear`

Example: `1.1.26.261`.

## Confirmed Behavior

- The local `qbook/release.ps1` is the official release entry point. Normal Visual Studio Debug builds remain unchanged.
- `NugetRevision.json` is created and maintained in the solution root. It contains the manually maintained `MainRevision`, the automatic `FossRevision`, and the deterministic, extensible third-party component snapshot plus its fingerprint.
- The current effective component state is compared with the snapshot in `NugetRevision.json` for every local release.
  - When it is unchanged, retain `FossRevision`.
  - When it is changed, increment `FossRevision`, replace the stored snapshot and fingerprint, and continue the release.
  - When `NugetRevision.json` is absent, create it with `MainRevision` `1`, `FossRevision` `1`, and the current snapshot.
- The script does not create a Git commit. After a release that changes `NugetRevision.json`, the user reviews and commits that file.
- The FOSS snapshot is not limited to NuGet. Preserve the existing effective component discovery for `qbook` and `qbookCsScript`, including their declared packages and the existing distributed runtime files.
- HTML FOSS-report generation, FOSS approval logic, and external review are out of scope.

## Version Rules

- `MainRevision` and `FossRevision` are numeric values from `0` through `65535`.
- `yy` is the two-digit local release year.
- `DayOfYear` is the release date's day number from `1` through `366`.
- Generate this exact four-part value for `AssemblyVersion`, `AssemblyFileVersion`, and `AssemblyInformationalVersion`; do not append a Git commit suffix.
- Multiple releases on the same day intentionally have the same date components; no additional daily sequence is part of this scope.

## Implementation Sequence

1. Add `NugetRevision.json` in the solution root.
   - Use a versioned JSON schema with `mainRevision`, `fossRevision`, `fingerprint`, and a generic `components` collection.
   - Initialize `mainRevision` and `fossRevision` to `1` and populate the current deterministic component snapshot and fingerprint.

2. Convert `qbook/updateFossState.ps1` to automatic state maintenance.
   - Keep the existing discovery scope, sorted canonical JSON, and .NET SHA-256 file and manifest hashing.
   - Remove approved-baseline validation and approval mode behavior.
   - Read `NugetRevision.json`, compare its stored fingerprint with the current fingerprint, and overwrite the stored `fossRevision`, fingerprint, and components only when the state changes.
   - Write the resulting state needed by release version generation without treating a change as an error.

3. Replace the version-generation inputs for `qbook`.
   - Change `qbook/updateAssemblyInfo.cs.ps1` to validate and read `NugetRevision.json` for Release builds.
   - Build the four version components from the stored main and FOSS revisions plus the current local two-digit year and day of year.
   - Emit exactly that four-part value for all three assembly-version attributes.
   - Update `qbook/qbook.csproj` so the official release path no longer requires `BuildRevision` or an approved FOSS baseline and passes the root revision file to the generator.

4. Apply the same Release version to `qbookCsScript`.
   - Add a Release-only generated-assembly-info target that reuses the `qbook` generator and the root revision file.
   - Ensure the generated file is compiled for Release.
   - Make the existing static version attributes apply only to Debug so Debug remains `1.0.0.0` and Release has no duplicate attributes.

5. Update the local release entry point and remove obsolete approval infrastructure.
   - Remove `BuildRevision` validation and forwarding from `qbook/release.ps1`.
   - Run the snapshot update before the existing local Visual Studio/MSBuild Release build.
   - Delete `qbook/approveFossState.ps1`, the obsolete `compliance/foss` approved-state and manifest files, and their project references.

6. Remove `.github/workflows/release-qbook.yml`.
   - Do not replace it with another hosted workflow.

## Acceptance Criteria

- The local release script completes without requiring a `BuildRevision` parameter or a GitHub runner.
- A Release build of both `qbook` and `qbookCsScript` carries the same version in the form `MainRevision.FossRevision.yy.DayOfYear`.
- Debug builds retain their established versions and do not update `NugetRevision.json`.
- An unchanged effective dependency state leaves `FossRevision` unchanged.
- A changed effective dependency state increments `FossRevision`, updates `NugetRevision.json`, and does not block the release.
- `NugetRevision.json` contains a deterministic component snapshot that is extensible beyond NuGet packages.
- The obsolete GitHub release workflow and approved-FOSS baseline mechanism are removed.

## Verification

No automated validation is registered for this solution. As resolved in STRUCTURE, the user runs the local release workflow and checks the generated release output, assembly versions, and any update to `NugetRevision.json` before committing that file.
