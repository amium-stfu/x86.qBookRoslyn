# Implementation Handoff: Major/Feature Release Version and BuildInfo

## Goal

Extend the implemented local qbook release workflow with the final four-part release version and a traceability document in the final qbook release output.

The Release version is:

`Major.Feature.Voss.Build`

Example: `1.1.1.26001`, where `26001` is the two-digit release year followed by the three-digit day of year.

## Confirmed Behavior

- `MajorRevision` and `FeatureRevision` are manually maintained in the source-controlled root `NugetRevision.json`.
- `FossRevision` is automatically incremented only when the effective, deterministic third-party component snapshot changes.
- `BuildId` is a monotonic value in `NugetRevision.json` and is incremented for every local official release, independent of dependency changes.
- The `Build` version component is the five-digit `yyDDD` value of the local release date. It remains the fourth numeric part of `AssemblyVersion`, `AssemblyFileVersion`, and `AssemblyInformationalVersion`.
- The user reviews and commits `NugetRevision.json` after every official local release so the build ID remains continuous across clones and workstations.
- `BuildInfo.md` is generated only in the final qbook release directory, `Setup\Release\bin\qbook`.
- `BuildInfo.md` contains the release version, exact UTC timestamp, full source commit, VOSS/FOSS revision and fingerprint, and the monotonic build ID.
- Debug builds remain unchanged. HTML FOSS-report generation, external FOSS approval, automatic Git commits, and ESP integration remain out of scope.

## Affected Files

| File | Required change |
| --- | --- |
| `NugetRevision.json` | Migrate the state from `mainRevision` to `majorRevision`, add `featureRevision` and `buildId`, and retain the FOSS snapshot and fingerprint. |
| `qbook/updateFossState.ps1` | Validate and maintain the revised state schema; preserve deterministic snapshot hashing, increment `fossRevision` only on a snapshot change, and increment `buildId` on every official release. |
| `qbook/updateAssemblyInfo.cs.ps1` | Generate `Major.Feature.Foss.yyDDD` for all Release assembly version attributes from the revised root state. |
| `qbook/updateBuildInfo.ps1` | Add a focused generator for `BuildInfo.md` from the revision state, UTC build time, and the current full Git commit. |
| `qbook/release.ps1` | Invoke snapshot maintenance before the existing local Release build, then create `BuildInfo.md` after a successful build. |
| `qbook/qbook.csproj` | Include `updateBuildInfo.ps1` as a project file; preserve the existing version-generator invocation and Debug behavior. |
| `qbookCsScript/qbookCsScript.csproj` | Continue reusing the shared qbook version generator so its Release version follows the new four-part format. |

## Implementation Steps

1. Migrate `NugetRevision.json` to the new state shape.
   - Replace `mainRevision` with `majorRevision` and retain its current value.
   - Add `featureRevision` with the initial value `1`.
   - Add `buildId` with the initial value `0`, so the next official release becomes build ID `1`.
   - Preserve `schemaVersion`, `fossRevision`, `fingerprint`, and `components`.

2. Update `qbook/updateFossState.ps1`.
   - Require and validate `majorRevision`, `featureRevision`, `fossRevision`, and `buildId` as non-negative numeric state fields.
   - Retain the current deterministic component discovery, sorted canonical manifest, and .NET SHA-256 hashing.
   - Increment `fossRevision` and replace the stored fingerprint/components only when the current fingerprint differs from the stored snapshot.
   - Increment `buildId` on every invocation used by the official release script, then persist the complete state back to `NugetRevision.json`.
   - Do not add an approval gate or make a changed FOSS snapshot fail the release.

3. Update Release assembly version generation in `qbook/updateAssemblyInfo.cs.ps1`.
   - Read the migrated root state and validate `majorRevision`, `featureRevision`, and `fossRevision` against the .NET version-part limit.
   - Calculate the Build component as local `yy` plus zero-padded day of year (`DDD`), for example `26001`.
   - Generate exactly `Major.Feature.Foss.Build` for `AssemblyVersion`, `AssemblyFileVersion`, and `AssemblyInformationalVersion`.
   - Do not append the Git commit to the informational version.
   - Preserve existing Debug-version behavior.

4. Add `qbook/updateBuildInfo.ps1`.
   - Accept the root revision-state path and the final qbook Release output directory.
   - Read the state and calculate the same four-part release version as the assembly generator.
   - Obtain the current repository `HEAD` as a full commit ID and capture the generation time in UTC ISO-8601 format.
   - Write `BuildInfo.md` to the supplied final output directory with the release version, UTC timestamp, source commit, `fossRevision`, fingerprint, and `buildId`.
   - Fail clearly if the revision state, output directory, or Git commit cannot be obtained.

5. Update local release orchestration in `qbook/release.ps1`.
   - Keep the existing Visual Studio/MSBuild discovery and local `Release|x86` build.
   - Run `updateFossState.ps1` before the build so the revision state and build ID are current for assembly generation.
   - Run `updateBuildInfo.ps1` only after a successful build, targeting `Setup\Release\bin\qbook`.
   - Do not add parameters, GitHub dependencies, or automatic Git commits.

6. Keep project integration aligned.
   - Add `updateBuildInfo.ps1` to the existing script items in `qbook/qbook.csproj`.
   - Leave the qbookCsScript generated assembly-info target in place; its use of the shared generator must produce the same Release version.

## Acceptance Criteria

- A local official release produces `Major.Feature.Foss.yyDDD`, for example `1.1.1.26001`, in both qbook and qbookCsScript Release assemblies.
- `NugetRevision.json` retains manual `majorRevision` and `featureRevision`, increases `fossRevision` only when the effective third-party snapshot changes, and increases `buildId` on every local official release.
- `Setup\Release\bin\qbook\BuildInfo.md` exists after a successful local release and contains the required version, UTC timestamp, full Git commit, FOSS revision/fingerprint, and build ID.
- Debug builds neither update `NugetRevision.json` nor generate `BuildInfo.md`.
- No FOSS change blocks the local release and no automatic Git commit is performed.

## Verification

No automated validation is registered for this solution. As resolved in STRUCTURE, the user runs the local release script and checks the generated release output, both Release assembly versions, `BuildInfo.md`, and the updated `NugetRevision.json` before committing that file.
